# Blast Radius: durable development instructions

## Scope and source of truth

- Build `blast`, a native Windows 11 x64 CLI for local change review and conflict-aware recovery of coding-agent sessions. The first supported target is user-selected local NTFS regular files in one workspace plus explicitly selected external paths.
- `Plan.md` is the only development plan. Update its status, evidence, decisions, and version table as work proceeds. Do not create parallel plans.
- Treat planned commands and capabilities as unimplemented until code and tests establish them. Label documentation-only findings, local observations, and tested behavior separately.

## Safety rules

- Define each required scope with fixed inclusion and explicit exclusion rules, persist the rule version and actual coverage, and show user-confirmed exclusions separately from read failures, unsupported types, and complete baselines. Never turn a failure into an exclusion or inherit `.gitignore` as a backup rule. Launch a protected command only after every required included file has a verified, durable content baseline and the session has committed `ready`.
- Model file presence as Present, Absent, or Unknown. A confirmed absence needs no content object; a zero-byte present file does. Read failures and incomplete scans are Unknown, never Absent. Backing up present C before removing a newly created file is required; do not fabricate an empty safety object for absent C when restoring a deletion.
- Never infer causation from timing alone. Keep attribution evidence separate from snapshot completeness and recoverability.
- Default `undo` to preview with an empty selection. Give changes stable IDs, require explicit selection and confirmation of the same fixed restore plan, and warn that unknown or time-correlated changes may include other programs' work. Snapshot completeness does not imply Agent attribution. Report `no operations applied` when nothing executes.
- Reject conflicting or unverifiable operations, missing or corrupt objects, redirected paths, unsupported file types, and uncertain race conditions. Check A's content, type, file identity, and path before apply; compare the result with B's logical content/type/metadata and record the new actual identity. Use that actual identity and the journal for idempotence and interrupted recovery. Never demand B's historical file ID after replacement or ignore A's ID before replacement.
- Keep associated rename operations grouped. Partial selection must be completed by the user or rejected; preflight conflict skips the whole group, while execution failure is logged as partial or uncertain and audited. Do not treat a Win32 error as proof that no change occurred. Unsupported directory rebuilds, name swaps, and cyclic or overwrite renames must be reported as `unsupported_to_apply` until tested.
- Before any destructive apply, durably commit the plan, verify required objects, create and verify an encrypted safety copy, and persist an operation intent. On restart, audit uncertain operations instead of blindly replaying them. Distinguish process-termination tests from independent system-crash or power-loss evidence. Do not add a force overwrite shortcut or use `git reset --hard` / `git clean` as recovery.
- Serialize `run`, `apply`, and interrupted-recovery audit for one state store with an OS-atomic cross-process exclusive lock. A new lock holder audits unresolved operations first. The lock does not replace target-state and path checks against other processes.
- Keep console cancellation in the shared production command path, with one handler scoped to each run. The callback only records the request; normal control flow performs bounded direct-child waiting, final scanning, and durable status updates. Do not re-broadcast Windows Ctrl+C, invent child exit code 130, or claim a completed session when baseline/final scan or persistence was interrupted. Preserve a known child code but prefer an explicit Blast failure exit when Blast cannot finish. Redirected or missing console input cannot be presented as keyboard Ctrl+C support; a direct child exit does not prove background writers stopped.
- Persist an auditable launch-possible state before starting a direct child. An uncertain child or unfinished durable run blocks later `run` and all modifying `apply` in that state store, including after wrapper termination; do not clear it from a PID lookup, time limit, or an `interrupted` label. Confirmed nonlaunch and durable complete runs may proceed. Shared production error handling must return a Blast failure result with observed child data and an explicit diagnostic persistence flag when expected storage writes fail; do not recursively retry a failed error record or add force unlock.
- Keep the checked directory-handle chain from the scope root through the direct parent protected through target mutation and verification. At final execution, compare **each held handle** with its historical identity in the confirmed plan, including intermediate ancestors; an earlier scan whose handles were released is insufficient. Preserve the live target handle when verifying modified or renamed files. An audited `in_doubt` plan blocks later `run` and `apply` in that state store until a verified reconciliation path exists; a new plan must not bypass it.
- Validate the final opened leaf with reparse following disabled before reading or changing it: actual path, ordinary file type, links, supported attributes, and NTFS stream list must agree with the confirmed prestate. Reject named streams and stream-query failures; retain the created file handle through verification of deletion recovery.
- Bind plan confirmation to a canonical immutable execution payload containing selected changes, operation kind/group, B/A, scope roots and baseline directory identities. Recompute its hash and compare the current session before apply; mutable safety copies, journal progress, and actual IDs stay outside that payload.
- Persist baseline identities for scope roots and existing directories, including empty directories. A replaced or new directory cannot inherit an Absent baseline from the final scan; reject restoration through historical directory drift.
- Keep the object store, database, and recovery journal outside protected roots. Exclude sensitive locations by default, but assume ordinary files can also contain secrets. Permit real-directory content backup only after verified authenticated encryption protects **all** persistent baseline, checkpoint, and pre-restore safety objects. Never write a generic plaintext temporary object or file contents into SQLite, logs, or reports. Control the location, permissions, lifetime, and failure cleanup of any necessary plaintext target staging. Same-user DPAPI is not an isolation boundary against a same-user Agent.
- A missing object key in a populated store is a failure to diagnose, never a reason to generate a replacement key. In reports distinguish implemented operation kind, verified snapshot object integrity, and still-unverified apply eligibility.
- The recorder and agent may share a Windows user. Do not claim tamper resistance, complete operation history, prevention of disclosure, or transactional recovery across files.
- Never alter global settings, install hooks, request elevation, read real credentials, publish, or run destructive tests against real user data without explicit authorization. Preserve any pre-existing files and Git changes.

## Implementation and verification

- Prefer C#/.NET 10, SQLite, a content-addressed object store, and minimal modules. Deterministic rules decide coverage, changes, conflicts, and restore eligibility; no model decides them.
- Use natural English for code identifiers and CLI text. Keep public README in English and `Plan.md` in Chinese.
- Use temporary directories and synthetic data for tests. Include real Windows NTFS integration tests, process interruption at recovery boundaries, concurrency and path tests, and fake-token leakage checks across ordinary files, new session content, safety copies, and excluded-path moves. Report OS, filesystem, dependency, and agent versions. Never weaken assertions to manufacture a pass or call process termination a power-loss test.
- Before the real-data gate passes, synthetic recovery is callable only through test tooling that creates its own temporary fixtures and internal entry points. Never classify an arbitrary user directory as synthetic by name or a `--synthetic` switch. Keep ordinary CLI `run` and `apply` on user paths disabled until the full gate is verified.
- Test workspace and explicit external file or directory scopes only on the same local NTFS volume for now. Use scope identity with relative paths; selecting one external file must not include its neighbors. Reject any scope intersecting the state store. Reject batch arguments whose cmd.exe semantics cannot yet be preserved.
- After plan approval, implement a complete baseline → command → final scan → report → explicit plan → verified restore chain before optional adapters. Phase 1 apply requires the minimal durable journal, verified objects and safety copies, and safe process-interruption handling. Keep cross-volume support disabled until the two-local-NTFS-volume test gate passes. Restore only selected working-tree files; do not roll back Git HEAD, index, stash, or commits. Document failed paths and actual limitations. Preserve the agent's own sandbox and approval settings.

## Continuing a session

1. Read `Plan.md` and inspect the current directory and Git status before editing.
2. Resume the earliest incomplete stage and review its acceptance gate. Verify upstream facts again if version-sensitive.
3. Update `Plan.md` only when a decision, status, test result, or risk actually changes. Mark `Done` only with concrete evidence.
4. Plan 0.2 was approved on 2026-09-29; continue stage 1 implementation without another plan-review pause. Ask only for actions that expand permissions, change global settings, incur cost, access private data, or publish. Do not mark stage 1 Done until every apply and real-data gate in `Plan.md` has evidence.
